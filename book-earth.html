Book Three · Earth

The Application Sanctum

Air was free but beyond your reach. Water flowed outward and left your hands.

Earth is different. Earth is ground you stand on and control completely — your own memory, your own rules, your own decisions about every byte.

First you learn to hold. Then you learn to split stone: one cache spread across many nodes, all of them agreeing.

Lesson Five

The Application Sanctum

Technique unlocked Stonehold holding data in your own memory

Scope of this lesson: one process, on one machine. Caching across many servers is Lesson 6. Caches the database keeps for itself are Lesson 7. Keeping these separate matters, because they fail in completely different ways.

The realm

An in-memory cache — also called a local cache or in-process cache — is data your application keeps in its own memory, inside the running program.

A process is one running copy of your program. When you start your server, that is a process. It has its own memory that no other program can see.

This is the fastest cache that exists. There is no network. There is no serialization — the object in the cache is a real object in your program, ready to use. A hit takes roughly 100 nanoseconds.

What you can hold here

You now have somewhere very fast to put things. The question is what to put there.

Inside your own process, two different kinds of thing are worth keeping — and they carry completely different risks.

Work you already did. A calculation, a parsed file, a rendered fragment. The inputs are still sitting right there in your program; you simply do not want to do the arithmetic twice. This can only go stale if the inputs change, and you control the inputs.

Data that came from somewhere else. A product row from the database, a response from another service. This copy can become wrong at any moment, because somebody else can change the original without telling you.

The first is nearly free of risk. The second is where Lesson 11 comes from.

Start with the safe one.

Memoization

Memoization is caching the result of a function so that calling it again with the same inputs returns the stored answer instead of recomputing it.

calculate_shipping(weight=2.5, zone="EU", express=false)
   → first call:  runs the calculation      12ms
   → second call: returns the stored answer  0.0001ms

The inputs form the key. The return value is the value. It is Lesson 2's key rule applied to a function signature — and it has the same failure mode. If the function secretly depends on something not in its arguments (today's date, a config setting, a database row), then that hidden input is missing from your key, and you will serve the wrong answer.

Memoization is only safe for functions where the same inputs always produce the same output.

The costs

Memory is shared with your application. A local cache lives in the same memory your app needs to run. An unbounded cache will consume it all and crash the process. Always set a maximum size — how the cache decides what to remove when it hits that limit is Lesson 10.

The cache dies with the process. Restart, deploy, crash, or scale down, and it is gone. Every deploy gives you a cold cache and the full cold-start problem from Lesson 2.

It does not scale with your data. A local cache can hold what fits in one machine's spare memory. That is a hard ceiling.

Redis, introduced carefully

Redis is a separate program that stores key-value data in memory and is reachable over a network. Many applications can talk to the same Redis instance.

It is important to be precise about this, because the terms get muddled constantly:

Local cacheRedis
Where it livesInside your processA separate program, usually another machine
Access time~100 nanoseconds~500 microseconds
SerializationNone — real objectsYes, every read and write
Survives restartNoYes
Shared between serversNoYes

Redis is roughly 5,000 times slower than a local cache. It is also roughly 200 times faster than a cross-continent request, and — the reason it exists — it is shared.

Both are “caching in the application layer.” They are not the same realm at all, and treating them as interchangeable is a source of real confusion.

What belongs in a local cache

Good candidates are small, hot, read-mostly, and tolerant of being slightly stale:

  • Configuration and feature flags
  • The category tree
  • Currency conversion rates
  • Results of expensive pure calculations
  • Very hot lookups you would otherwise send to Redis thousands of times a second

Bad candidates are large data, anything that must be exactly current, and anything personal to one user — because your process serves many users, and a key that forgets to identify the user will hand one person's data to another.

At the Storefront

Memoize the shipping and price calculations. Keep the category tree in a local cache with a 5-minute TTL.

Leave the product data alone for now. You are about to find out why.

The misconception to kill

“In-memory cache means Redis.”

Local is inside your process — no network, no serialization, gone on restart, invisible to your other servers. Redis is across a network and shared. The gap between them is three orders of magnitude, and the shared part is the entire reason the next lesson exists.

The closing hook

You now run two application servers behind a load balancer, because one was not enough.

An administrator changes a product's price from £25 to £20.

Server A handles the write and updates its local cache. Server B knows nothing about it and still holds £25.

Refresh the page a few times. £20. £25. £20. £25. The price changes depending on which server happens to answer.

Two caches. One key. Two different values. Which one is telling the truth?

Neither. That is the problem, and it is what Stonesplit exists to solve.

Lesson Six

The Distributed Cache Tribes

Technique unlocked Stonesplit one cache spread across many nodes

The problem, stated properly

You have 10 application servers. Each has its own local cache. This gives you three distinct problems.

1. They disagree

The scenario that ended Lesson 5, now with ten servers instead of two. It is worth walking through slowly, because “the same code produced two different answers” sounds impossible.

The code is identical on every server. What differs is when each one last looked.

09:00   Server A   reads price £25 from the database, caches it
09:00   Server B   reads price £25 from the database, caches it

09:30   Admin      changes the price to £20 in the database
        Server A   handled that write, so it updates its own cache   → £20
        Server B   was not involved. It has no idea anything happened → £25

09:31   Customer   request lands on Server A    → sees £20
09:31   Customer   refreshes, lands on Server B → sees £25

Neither server has a bug. Both are running exactly the code you wrote. They disagree because a cache is a copy, and each server made its own copy at its own moment.

So with ten servers you do not have one cache with a stale entry. You have ten separate caches, each stale in its own way.

2. Your hit ratio collapses

The same product must be loaded and stored ten separate times — once per server. Each server only sees a tenth of the traffic, so each takes far longer to warm up. You are paying ten times the memory for a fraction of the benefit.

3. You cannot invalidate

Change something, and you would need to reach into all ten processes to remove the stale copy. There is no mechanism to do that. As you add servers, it gets worse.

A distributed cache solves all three: one shared cache that every server reads from and writes to.

Server A ─┐
Server B ─┼─→  Shared cache  ─→  Database
Server C ─┘

One value. One place to update. One warm-up. All ten servers benefit from the first one's miss.

In practice, for most teams, that shared cache is Redis. So the rest of this lesson is about what Redis actually gives you, where it genuinely shines, and what it costs.

What Redis gives you

You met Redis in Lesson 5 as “a separate program that stores key-value data in memory.” Here is what that buys you beyond simply being shared:

  • Every server sees the same value. The reason this lesson exists.
  • It survives your application restarting. Deploys no longer empty your cache.
  • Sub-millisecond reads. Slower than local memory, far faster than a database.
  • TTL is built into every key. You do not implement expiry — you set it and Redis honours it.
  • Eviction is built in. When memory fills, Redis decides what to drop using a policy you choose (Lesson 10).
  • Operations are atomic. Two servers incrementing the same counter cannot overwrite each other, because the increment happens inside Redis rather than in your code.
  • It can tell your servers when something changed. Redis can publish a message that every server receives — the mechanism behind event-driven invalidation (Lesson 11).
  • It stores more than strings. Counters, lists, sets and sorted sets are native, which makes some problems trivial that are awkward anywhere else.

Where Redis is genuinely excellent

ScenarioWhy Redis specifically
Session storageEvery server needs the same session. The original use case, and still the most common.
Rate limitingAtomic counters with an expiry — correct under concurrency without you writing locks
Counters and leaderboardsSorted sets do natively what is genuinely awkward in a relational database
Shared cache in front of a databaseThe case this course is about
Simple queuesLists as job handoff between services

A few of these in practice:

Session — store it with a 30-minute expiry
    SET session:a91f3c "{...}" EX 1800

Rate limiting — count this minute's requests, expire the counter after it
    INCR   ratelimit:user:42:0930
    EXPIRE ratelimit:user:42:0930 60

Leaderboard — record a score, then read the top ten instantly
    ZADD      leaderboard 4820 "player:17"
    ZREVRANGE leaderboard 0 9

Caching — store a product for five minutes
    SETEX product:42 300 "{...}"
    GET   product:42

Look at the rate-limiting example. Two servers can run INCR on the same key at the same moment and the count is still correct, because Redis performs the increment itself. Doing that with a plain read-modify-write in your own code — read 10, add 1, write 11, twice, concurrently — loses one of the increments.

This is the read-modify-write race, and Redis solves it by doing the work for you.

How Redis scales

Three mechanisms, and you mainly need to know that they exist and what they cost.

Replicas. Copies of the data on other nodes. They serve reads and they mean a dead node does not take its data with it. The cost is replica lag — the gap between a write landing on the primary and appearing on the replica. Usually milliseconds, never zero, and during that window a read from a replica returns the old value.

Redis Cluster. When one machine's memory is not enough, Cluster splits your keys across several nodes. Every key is assigned to one of 16,384 hash slots, and each node owns a range of slots. Add a node and it takes over some slots from the others.

The sentence to take away:

Your key lives on exactly one node.

Failover. When a primary dies, one of its replicas is promoted. Two things this costs you: any writes that had not yet reached the replica are lost, and there is a gap of seconds while the failure is detected and the promotion happens, during which requests to that node fail.

Which leads to a rule you should design around now:

Your application must keep working when the cache is unavailable. Slower, but working. Treat a cache error as a miss, not as an exception.

If it cannot do that, what you have built is not a cache. It is a database with no durability guarantees. Lesson 13 will make you test this.

The downsides

Redis is not free, and the costs are worth stating plainly:

  • It is a network hop. Roughly 5,000 times slower than local memory. Do not send it a request you could have answered in-process.
  • It is another thing that can go down. See the rule above.
  • Memory is expensive. RAM costs far more per gigabyte than disk. A cache that holds everything is usually a cache that costs more than the problem.
  • Everything is serialized. Objects go in as bytes and come back as bytes, and that conversion is not free.
  • It is not a database. Redis can persist to disk, but that is not what it is for. Do not store anything there that you cannot afford to lose.
  • One key lives on one node. A single very popular key concentrates all of its traffic on one machine, and adding nodes does not help — the key still lives in exactly one place.

That last one is not a flaw you can configure away. It is a property of how sharding works, and the Latency Lord is about to notice it.

At the Storefront

Move product details, price, and reviews to shared Redis. Pick a key scheme and a shard key. Keep the category tree local — it is small, it is read constantly, and slight staleness is harmless. Two realms, used together, on purpose.

The misconception to kill

“A shared cache makes my data consistent.”

It makes your servers agree with each other. All ten can now confidently serve the same stale price. Agreement is not correctness, and the gap between them is Lesson 11.

The Forge

The Latency Lord counts the nodes and studies the traffic flowing to each.

They are evenly spread — except for one. A single key, asked for more often than every other key combined. The front-page item. The one everybody wants.

He does not need to attack every node in the cluster. He needs the one node that holds that key.
